## Release Principles

- Release dibuat dari commit yang immutable dan seluruh required CI gate lulus.
- Staging dan production menggunakan artifact yang sama.
- Tidak ada edit source manual pada server.
- Setiap release memiliki owner, identifier, changelog, evidence, migration plan,
  rollback/forward-fix plan, dan communication record.
- Release harus reproducible dari lock file dan workflow yang versioned.
- Semantic Versioning digunakan: MAJOR.MINOR.PATCH.

## Versioning Rules

- MAJOR: breaking contract, migration, API, module, atau public behavior.
- MINOR: backward-compatible feature, module capability, atau setting capability.
- PATCH: backward-compatible bug fix, security fix, documentation, atau maintenance.
- Pre-release memakai suffix seperti alpha, beta, atau rc hanya bila diperlukan.
- Release tag dan artifact name menggunakan version yang sama.
- Breaking change wajib memiliki migration guide dan approval architect/product.

## Release Lifecycle

### 1. Prepare

Release owner:

- memastikan scope feature/fix selesai dan acceptance evidence tersedia;
- memastikan changelog, release notes, known issues, dan documentation diperbarui;
- memastikan version, release tag, dan dependency lock files konsisten;
- memastikan Open Decision yang memengaruhi release sudah resolved atau diberi
  explicit risk acceptance;
- menyiapkan migration, config, SystemSetting changes, backup, dan rollback plan.

### 2. Verify

QA dan CI memverifikasi:

- required quality, test, coverage, build, browser, and security gates;
- migration fresh-install dan upgrade;
- generated module structure, manifest, permission, audit, dan ULID behavior;
- critical starter kit, AccessControl, UserManagement, AuditLog, dan
  SystemSetting flows;
- performance/resilience evidence sesuai release scope;
- forbidden dependency and secret scan.

Release tidak boleh dipromosikan bila ada critical/high security finding,
migration failure, authorization failure, generator regression, atau critical
browser flow failure.

### 3. Package

CI membuat artifact immutable yang berisi:

- source sesuai commit;
- Composer/vendor result sesuai lock file atau reproducible install metadata;
- frontend production build;
- migration and release manifest;
- release version, commit SHA, build timestamp, dan dependency evidence.

Artifact tidak boleh berisi .env production, secret, test credential, local dump,
atau debug configuration. Checksum dan retention artifact dicatat.

### 4. Stage

- Deploy artifact ke staging menggunakan protected workflow.
- Jalankan migration hanya setelah compatibility check dan backup evidence.
- Jalankan health/readiness check, module registry diagnostic, dan smoke test.
- QA melakukan critical user journey, permission matrix, responsive/accessibility,
  impersonation, audit, dan SystemSetting verification.
- Catat result, issue, workaround, dan approval pada release record.

### 5. Approve

Production approval membutuhkan:

- release owner approval;
- QA acceptance;
- DevOps readiness;
- backup/restore evidence;
- migration and rollback plan;
- security gate pass;
- communication plan;
- protected environment approval pada CI.

### 6. Production Deploy

- Freeze artifact dan commit yang dipromosikan.
- Verify target capability: DigitalOcean Ubuntu atau cPanel.
- Enable maintenance mode bila diperlukan.
- Drain/pause queue sesuai migration plan.
- Run compatible migration.
- Activate application artifact and configuration.
- Clear/rebuild cache sesuai runbook.
- Start/verify queue worker and scheduler.
- Run health, readiness, module registry, and smoke test.
- Monitor error rate, latency, queue, database, Redis, audit, and critical flows.

### 7. Close

Release owner:

- mengumumkan status success, partial, atau rollback;
- menyimpan deployment evidence dan release identifier;
- menutup maintenance mode;
- memastikan monitoring dan backup normal;
- mencatat known issue dan follow-up owner;
- memperbarui release record dan changelog.

## Release Checklist

### Scope and Documentation

- [ ] Scope dan acceptance criteria selesai.
- [ ] Changelog dan release notes diperbarui.
- [ ] Breaking changes dan migration guide tersedia.
- [ ] Documentation, context, and operational runbook diperbarui.
- [ ] Known issues dan risk acceptance tercatat.

### Quality and Security

- [ ] CI required checks lulus.
- [ ] Coverage threshold lulus.
- [ ] Frontend build lulus.
- [ ] Browser/accessibility critical flows lulus.
- [ ] Dependency, CodeQL, secret, and forbidden package scan lulus.
- [ ] No critical/high security finding terbuka.

### Data and Operations

- [ ] Migration fresh dan upgrade diverifikasi.
- [ ] Migration backward compatibility direview.
- [ ] Backup dan restore evidence tersedia.
- [ ] RTO/RPO SystemSetting sesuai target environment.
- [ ] Queue, scheduler, Redis, storage, dan health check siap.
- [ ] Deployment/rollback owner tersedia.

### Promotion

- [ ] Immutable artifact dibuat dan checksum dicatat.
- [ ] Staging deployment lulus.
- [ ] QA approval tercatat.
- [ ] Production approval tercatat.
- [ ] Smoke test production lulus.
- [ ] Monitoring pascadeploy diperiksa.

## Migration Rules

- Gunakan expand-and-contract untuk perubahan yang memerlukan compatibility.
- Migration harus aman terhadap deploy overlap dan retry bila memungkinkan.
- Destructive migration dipisahkan dari release yang mengubah consumer.
- Backup dan recovery plan wajib tersedia sebelum destructive action.
- Rollback aplikasi tidak otomatis rollback database.
- Bila rollback migration tidak aman, gunakan forward-fix dan dokumentasikan.
- Migration status dan schema checksum disimpan sebagai release evidence.

## Rollback and Forward-Fix

Rollback dipicu bila health/readiness gagal, error rate melewati threshold,
critical user flow gagal, data integrity berisiko, atau security incident terjadi.

Prosedur:

1. Stop promotion dan record release status.
2. Preserve log, audit, deployment, and diagnostic evidence.
3. Decide rollback artifact, disable unsafe module, maintenance mode, atau
   forward-fix.
4. Pause/drain queue bila side effect atau schema compatibility terpengaruh.
5. Deploy previous compatible artifact atau approved fix.
6. Jangan menghapus audit evidence.
7. Run health, readiness, migration, queue, smoke, and critical flow checks.
8. Communicate impact dan residual risk.
9. Buat post-release incident/action record.

Destructive migration tidak boleh menjadi prasyarat rollback. Bila previous
artifact tidak kompatibel dengan schema baru, forward-fix adalah jalur resmi.

## Platform Release Notes

### DigitalOcean Ubuntu

Verify SSH deploy user, artifact transfer, release activation, process
supervisor, queue worker, scheduler, web server, TLS, firewall, database,
Redis, backup, and monitoring.

### cPanel

Verify account-scoped deployment credential, PHP version/extensions, document root
ke public, storage permission, cron/queue capability, database, Redis/external
cache, TLS, backup, and environment secret configuration.

Platform difference tidak boleh mengubah acceptance gate aplikasi.

## Release Record

Setiap release record menyimpan:

- version, tag, commit SHA, artifact checksum;
- release owner, reviewer, QA, DevOps, approval timestamp;
- changed modules, migration, SystemSetting, and config impact;
- CI, security, browser, performance, and smoke evidence;
- deployment start/end, environment, result;
- rollback/forward-fix decision;
- known issues, communication, and follow-up actions.

## Acceptance Criteria

- Release dapat dibuat dari commit dan artifact yang dapat diverifikasi.
- Promotion staging-to-production menggunakan artifact yang sama.
- Semua required gate dan approval tercatat.
- Migration, backup, smoke, health, queue, dan rollback evidence tersedia.
- Release dapat dibatalkan tanpa kehilangan audit evidence.
- DigitalOcean dan cPanel memiliki preflight checklist.
- Developer, QA, dan DevOps dapat menjalankan proses tanpa asumsi lisan.
