# 05.03 ADR-0001: DDD-lite Modular Monolith Architecture

## Decision Scope

Keputusan ini berlaku untuk baseline 00 sampai 05 dan menjadi dependency untuk
system design, module specification, implementation, testing, dan deployment.
Project turunan boleh menambah module, tetapi tidak boleh melanggar boundary
tanpa ADR baru.

## Context

Starter kit harus reusable lintas project dan dapat dipahami serta diikuti oleh
developer maupun AI coding assistant. Monolith Laravel memberi operational
simplicity untuk baseline awal, tetapi folder berbasis technical concern saja
akan membuat ownership, dependency, permission, dan testing boundary kabur.

Microservices tidak dipilih untuk baseline pertama karena menambah biaya
deployment, distributed failure, observability, network contract, dan data
coordination sebelum kebutuhan scale benar-benar terbukti.

## Decision

Project menggunakan DDD-lite Modular Monolith dengan prinsip:

- Laravel 13, PHP 8.4+, React, Inertia, TypeScript, Vite, Tailwind, shadcn/ui.
- Domain/system module lokal pada app/Modules/{Domain}/{SubModule}.
- Reusable generator, registry, console, stub engine, contract, dan kernel
  service berada pada packages/StarterKit.
- Setiap module memiliki purpose, owner, manifest, provider, permission identity,
  contract, event, database boundary, frontend ownership, test, dan README.
- Layer module adalah Domain, Application, Infrastructure, Presentation, Database,
  Routes, dan Tests.
- Cross-module communication memakai public contract, DTO, public event, atau
  shared value object yang telah disepakati.
- Direct concrete dependency lintas module dilarang.
- Setiap module memiliki communication layer sendiri.
- Module invalid diisolasi; module valid lain tetap bootstrap.
- Semua identifier persistence dan boundary menggunakan ULID.
- Authorization menggunakan allow permission dan policy rule; explicit deny model
  tidak termasuk baseline.
- AccessControl, UserManagement, AuditLog, dan SystemSetting adalah initial
  System modules.
- Auth, profile, notification, dan settings dasar starter kit diintegrasikan,
  bukan dibangun ulang.
- Wayfinder dan Laravel Boost dilarang; route frontend menggunakan Ziggy.

## Boundary Rules

- Domain tidak bergantung pada Laravel, Eloquent, HTTP, queue vendor, atau UI.
- Infrastructure mengimplementasikan contract/port dan menjadi adapter framework.
- Presentation hanya menerjemahkan transport request/response dan memanggil
  application use case.
- Application mengorkestrasi use case tanpa mengambil alih invariant domain.
- Database schema dan migration dimiliki module yang memiliki data.
- Permission vocabulary dimiliki module asal; AccessControl melakukan discovery
  dan synchronization.
- Runtime setting dapat disimpan global oleh SystemSetting, tetapi schema,
  default, validation, dan behavior tetap dimiliki module asal.
- Audit recording memakai public contract; AuditLog tetap append-only dan
  sensitive payload wajib disaring.

## Module Communication

Synchronous call wajib menggunakan contract dan DTO. Asynchronous behavior
menggunakan typed event dengan correlation ID ULID. Consumer tidak boleh
mengakses private model, repository, controller, atau implementation module lain.

Shared value object hanya digunakan bila immutable, stabil, dan disetujui
sebagai shared contract. Dependency wajib tercatat pada module.json dan diuji
melalui contract/dependency test.

## Consequences

### Positive

- Module ownership dan perubahan lebih mudah dilacak.
- Testing dapat dibagi menurut domain, application, integration, dan contract.
- Monolith lebih sederhana untuk Laragon, VPS, dan cPanel.
- Generator dapat menghasilkan struktur konsisten.
- Project turunan dapat menambah domain tanpa mengubah kernel.
- AI assistant memiliki context boundary yang eksplisit.

### Negative

- Membutuhkan disiplin dependency dan review boundary.
- Contract/DTO/event menambah boilerplate.
- Registry dan isolated bootstrap menambah kompleksitas kernel.
- Database tetap shared sehingga migration discipline wajib.
- cPanel capability dapat membatasi queue, Redis, scheduler, atau worker.

### Operational Impact

- CI wajib menjalankan module discovery, contract, generator, dan forbidden
  dependency tests.
- Release wajib memverifikasi migration, registry, queue, cache, health, dan
  smoke flow.
- Deployment dapat memakai DigitalOcean Ubuntu atau cPanel sesuai capability.
- RTO/RPO operational target dikelola melalui SystemSetting dan wajib diaudit.

## Rejected Alternatives

| Alternative | Reason Rejected |
|---|---|
| Technical-layer monolith tanpa module boundary | Ownership dan dependency mudah menjadi global coupling |
| Microservices | Operational/distributed complexity belum justified untuk baseline |
| Full tactical DDD | Terlalu berat untuk reusable starter slice pertama |
| Laravel package untuk setiap business module | Distribution dan versioning overhead belum diperlukan |
| Direct model/service access lintas module | Merusak encapsulation dan membuat refactor berisiko |

## Validation and Compliance

ADR dianggap terlaksana bila:

- module generator menghasilkan boundary yang ditentukan;
- registry dapat mengisolasi module invalid;
- contract/dependency test mencegah direct concrete dependency;
- all identifier tests memverifikasi ULID;
- AccessControl, AuditLog, dan SystemSetting integration tests lulus;
- forbidden dependency scan tidak menemukan Wayfinder atau Laravel Boost;
- clean Laragon bootstrap dan CI pipeline lulus.

## Revision Policy

Perubahan arsitektur yang memengaruhi module boundary, package boundary,
communication contract, identifier, authorization model, atau deployment model
wajib membuat ADR baru atau superseding ADR. Jangan mengubah keputusan ini
hanya melalui code commit.
