## Workflow Principles

- Requirement dan acceptance criteria datang sebelum implementation.
- Design contract ditetapkan sebelum code lintas boundary.
- Module lintas dependency menggunakan public contract/communication layer.
- Test ditulis bersama behavior, bukan setelah semua code selesai.
- AI wajib membaca context, spec, pattern, dan test terkait sebelum mengubah file.
- Open Decision tidak boleh diselesaikan dengan asumsi diam-diam.
- Setiap task kecil harus meninggalkan repository dalam kondisi verifiable.

## Context Loading Before Work

1. Baca `AGENTS.md` dan `00.05-DOCUMENTATION-CONTEXT.md`.
2. Baca scope, glossary, dan baseline direction yang relevan.
3. Baca requirement/user story dan acceptance criteria.
4. Baca system/security/database/API design yang terdampak.
5. Baca implementation pattern dan test yang sudah ada.
6. Tulis plan singkat, file yang akan diubah, dan verification command.

## Delivery Flow

```text
Context and Task
      |
      v
Requirement + Acceptance Criteria
      |
      v
Design Contract + Dependency Review
      |
      v
Test/Verification Plan
      |
      v
Implementation
      |
      v
Formatter + Static Analysis + Test + Security Scan
      |
      v
Pull Request Review
      |
      v
Merge to protected main
      |
      v
Staging / Release / Operations
```

## Module Development Flow

1. Pastikan module/submodule tercatat dalam `module.json` design.
2. Jalankan `php artisan module:make System {Submodule}`.
3. Jalankan `--dry-run` dan review generated plan.
4. Generate dengan output lengkap dan commit generated baseline.
5. Tetapkan domain contract, application use case, event, dan communication layer.
6. Tetapkan migration, ULID, index, relation, dan security policy.
7. Implementasikan test domain, feature, integration, dan browser bila perlu.
8. Jalankan `module:validate`, `module:discover`, dan test suite.
9. Dokumentasikan API, permission, audit event, dan operational impact.

## Feature Development Flow

Feature generator CRUD/API universal bukan baseline pertama. Untuk feature baru:

1. Tautkan ke module owner.
2. Tambahkan/ubah requirement dan user story.
3. Tetapkan API/UI/data/security contract.
4. Implementasikan pada layer yang benar.
5. Pastikan component frontend mengikuti ownership module.
6. Pastikan authorization server-side.
7. Pastikan audit/idempotency/rate limit impact ditangani.

## Branch and Pull Request Workflow

```text
feature/<short-description>
        |
        v
Pull Request -> protected main
```

- Branch feature dibuat dari `main` terbaru.
- Direct push ke `main` dilarang.
- Semua perubahan masuk melalui Pull Request.
- Minimal satu reviewer.
- CODEOWNERS wajib mereview framework, kernel, security, dan deployment.
- Squash merge digunakan kecuali ada alasan histori khusus.
- Squash merge wajib untuk Pull Request biasa; merge commit hanya untuk release
  besar atau kebutuhan histori yang disetujui.
- Branch feature dihapus setelah merge.

### Branch Naming

Format:

```text
<type>/<scope>/<short-description>
```

Contoh:

```text
feat/access-control/add-role-assignment
fix/user-management/prevent-deleted-login
docs/database/add-ulid-rules
security/impersonation/block-super-system-target
```

Branch menggunakan lowercase dan kebab-case. Type yang didukung: `feat`, `fix`,
`refactor`, `docs`, `test`, `chore`, `security`, `release`, dan `hotfix`.

## Pull Request Checklist

- [ ] Requirement/user story dan acceptance criteria tertaut.
- [ ] Design contract dan module boundary diperbarui bila terdampak.
- [ ] Test baru tersedia atau alasan pengecualian dijelaskan.
- [ ] Migration, ULID, FK, index, soft delete, dan rollback direview.
- [ ] Authorization, impersonation, audit, redaction, dan scope direview.
- [ ] Rate limit, idempotency, queue, cache, dan deployment impact direview.
- [ ] Generated output tidak menimpa file tanpa `--force`.
- [ ] Forbidden dependency tidak muncul.
- [ ] Documentation, glossary, changelog, atau ADR diperbarui.
- [ ] CI dan security scan lulus.
- [ ] Tidak ada Open Decision kritis yang disembunyikan.

## Commit Convention

Gunakan Conventional Commit dengan scope subsystem:

```text
<type>(<scope>): <description>
```

Contoh scope: `starter-kit`, `kernel`, `generator`, `module-console`,
`access-control`, `user-management`, `audit-log`, `system-setting`, `api`,
`database`, `frontend`, `security`, `ci`, dan `docs`.

## Required Quality Gates

```bash
php artisan starter:verify
php artisan module:validate --json
php artisan module:discover --json
vendor/bin/pint --test
vendor/bin/phpstan analyse
npm run format:check
npm run lint
npm run typecheck
php artisan test
npm run build
```

CI juga menjalankan CodeQL, dependency scan, forbidden dependency check, dan
browser/accessibility test sesuai perubahan.

## Documentation Workflow

- Requirement change memperbarui functional/NFR/user story.
- Design change memperbarui system/API/database/security/UI design.
- Implementation change memperbarui coding/module/test/workflow docs.
- Deployment change memperbarui environment/CI/release/operations docs.
- Boundary, stack, policy, atau decision change wajib memiliki ADR.
- Terminology baru masuk glossary.

## Release Readiness

Sebelum release ke staging/production:

- Semua `Must` acceptance criteria verified.
- Migration upgrade dan rollback plan direview.
- Backup, restore, observability, dan incident contact tersedia.
- Security critical finding tertutup.
- Changelog, known issue, dan version diperbarui.
- Staging smoke test lulus.

## Emergency Change

Emergency change tetap menggunakan branch dan Pull Request. Jika bypass review
diperlukan karena incident, owner mencatat alasan, reviewer setelah kejadian,
test evidence, dan follow-up ADR dalam 24 jam.
