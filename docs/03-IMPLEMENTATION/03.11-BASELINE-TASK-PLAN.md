## Planning Rules

- Task dikerjakan berurutan bila memiliki dependency.
- Setiap task menghasilkan code, test, atau documentation yang dapat direview.
- Tidak ada task selesai tanpa acceptance criteria dan verification evidence.
- Baseline dibatasi pada generator, module console, AccessControl,
  UserManagement, AuditLog, dan SystemSetting.
- Auth, profile, notification, dan settings default starter kit diintegrasikan,
  bukan dibangun ulang.
- Module baru dibuat melalui generator resmi; exception manual membutuhkan ADR.

## Baseline Environment

Target environment baseline pertama adalah **Laragon pada Windows**. Local
verification menggunakan PHP/Laravel dari Laragon, PostgreSQL, Redis, Node.js,
dan npm yang tersedia pada environment tersebut. Docker dan Linux staging bukan
gate baseline pertama; keduanya menjadi target verifikasi pada fase deployment
berikutnya.

## Phase 0 — Context and Repository Verification

### T-001 Verify Runtime and Starter Kit

**Depends on:** None

Verifikasi pada Laragon: PHP 8.4+, Laravel 13, React starter kit, Inertia, TypeScript, Vite,
Tailwind, shadcn/ui, PostgreSQL, Redis, dan Ziggy. Catat versi aktual dan
pastikan migration serta starter kit dapat boot pada environment bersih.

**Acceptance:** Project dapat boot dan starter kit default dapat diakses.  
**Verify:** php artisan about, php artisan migrate:fresh, npm run build.

### T-002 Remove Forbidden Dependencies

**Depends on:** T-001

Audit composer, npm, config, source, generated output, dan documentation.
Hapus total Wayfinder dan Laravel Boost. Tetapkan Ziggy sebagai route helper
frontend.

**Acceptance:** Tidak ada dependency atau referensi aktif ke package forbidden.  
**Verify:** Composer/npm audit dan repository search menghasilkan zero result.

### T-003 Establish Baseline Quality Gate

**Depends on:** T-001

Aktifkan Pint, PHPStan/Larastan, Pest/PHPUnit, ESLint, TypeScript check, Vitest,
dan build. Tambahkan CI job dasar untuk quality gate dan dependency scan.

**Acceptance:** Quality gate dapat dijalankan lokal dan CI.  
**Verify:** Command pada 03.10-TEST-PLAN.md lulus.

## Phase 1 — Kernel and Module Contract

### T-004 Create Package Boundary

**Depends on:** T-001, T-003

Buat packages/StarterKit dan Composer path repository untuk development.
Pisahkan generator, registry, console, stub engine, contract, dan kernel service.

**Acceptance:** Package autoload dan service provider dapat dimuat tanpa business module.  
**Verify:** Composer autoload test dan application boot test.

### T-005 Implement Module Manifest and Lifecycle Contract

**Depends on:** T-004

Implementasikan module.json, module.php, provider contract, status, dependency,
permission source, schema validation, serta lifecycle Discovered, Validated,
Registered, Enabled, Running, Disabled, dan Invalid.

**Acceptance:** Manifest invalid menghasilkan diagnostic tanpa menghentikan module valid.  
**Verify:** Registry unit, contract, dan integration test.

### T-006 Implement Module Communication Contract

**Depends on:** T-005

Sediakan contract, DTO, event boundary, public communication layer, dan
propagasi ULID correlation ID serta actor ID.

**Acceptance:** Cross-module test hanya memakai public contract atau event.  
**Verify:** Contract test dan static dependency rule.

## Phase 2 — Generator and Console

### T-007 Implement Stub Registry and Default-v1 Profile

**Depends on:** T-005, T-006

Register stub dari 03.08-STUB-SPEC.md. Implementasikan profile `default-v1`
dengan directory DDD-lite, manifest, permission source kosong, provider, route
entry point, dan README minimum. Test, migration, frontend, dan business logic
dibuat pada tahap implementasi module, bukan oleh generator baseline.

**Acceptance:** Profile menghasilkan output reproducible untuk input yang sama.  
**Verify:** Snapshot dan generated structure test.

### T-008 Implement Safe Filesystem Engine

**Depends on:** T-007

Implementasikan dry-run, conflict detection, force/yes, staging, atomic
promotion, cleanup, backup/restore, dan secret redaction.

**Acceptance:** Conflict, failure, dan overwrite behavior sesuai specification.  
**Verify:** Filesystem safety, failure cleanup, dan restore test.

### T-009 Implement module:make

**Depends on:** T-007, T-008

Implementasikan command module:make dengan validasi naming, namespace, path,
dependency, profile, forbidden package, human output, dan JSON output.

**Acceptance:** UserManagement dapat dibuat dari command dengan skeleton
`default-v1` setelah existing module inventory dan validation selesai. File
business, test, migration, dan frontend dilengkapi pada tahap module.
**Verify:** Command feature test dan clean workspace smoke test.

### T-010 Implement Module Lifecycle Console

**Depends on:** T-005, T-009

Implementasikan module:list, inspect, discover, validate, enable, disable,
diagnostic, dan health command dengan exit code serta JSON schema stabil.

**Acceptance:** Operator dapat menemukan, memvalidasi, dan mengisolasi module invalid.  
**Verify:** Console integration test dan JSON contract test.

## Phase 3 — AccessControl and UserManagement

### T-011 Implement AccessControl Baseline

**Depends on:** T-005, T-009, T-010

Integrasikan Spatie Permission. Implementasikan role, permission, assignment,
policy, effective allow, permission discovery dari permissions.php, seed role
baseline SuperSystem, public authorization capability, dan privileged visibility.

**Acceptance:** AccessControl menjadi module baseline pertama, contract authorization
tersedia, dan role, permission, sync, policy, serta SuperSystem behavior lulus.
**Verify:** AccessControl feature, policy, permission, visibility, dan contract tests.

### T-012 Implement UserManagement Baseline

**Depends on:** T-011

Integrasikan model users starter kit. Implementasikan create, read, update,
active/inactive, soft delete, restore, public contract, dan ULID behavior tanpa
menduplikasi authentication starter kit atau authorization implementation.

**Acceptance:** UserManagement dapat berjalan setelah AccessControl contract
tersedia, tidak menduplikasi auth starter kit, dan inventory tidak menunjukkan
duplicate ownership.  
**Verify:** Feature, database, contract, policy, dan API tests.

### T-013 Integrate UserManagement Authorization

**Depends on:** T-012

Hubungkan UserManagement dengan public authorization capability dari AccessControl.
Cross-module call wajib menggunakan public contract atau event; concrete model,
repository, dan private implementation tidak boleh diimpor.

**Acceptance:** Lifecycle user dan authorization matrix lulus tanpa mengganti auth.  
**Verify:** Feature, database, policy, dan API tests.

### T-014 Implement Impersonation

**Depends on:** T-013, T-015

Implementasikan permission user.impersonate, reason wajib, target SuperSystem
selalu ditolak, actor/target/status/start/end tersimpan, audit event, explicit
exit, dan frontend banner/indicator.

**Acceptance:** Impersonation aman, traceable, dan tidak mengubah privilege permanen.  
**Verify:** Positive/negative feature, security, audit, dan browser tests.

## Phase 4 — AuditLog and SystemSetting

### T-015 Implement AuditLog

**Depends on:** T-005, T-006, T-011

Implementasikan append-only audit record, redaction, correlation ID, visibility
scope, retention metadata, dan public recording contract.

**Acceptance:** Event wajib tercatat dan scoped visibility tidak bocor.  
**Verify:** Audit integration, authorization, redaction, dan retention tests.

### T-016 Implement SystemSetting Core

**Depends on:** T-014

Implementasikan global setting storage, schema registry contract, validation,
safe default, cache, activation, failure diagnostic, authorization SuperSystem,
dan reason wajib.

**Acceptance:** Setting valid langsung aktif, setting invalid memakai safe default,
dan perubahan selalu diaudit.  
**Verify:** SystemSetting feature, cache failure, validation, dan audit tests.

### T-017 Register Baseline Runtime Settings

**Depends on:** T-015

Register rate limit per actor/endpoint, idempotency 24 jam dengan payload hash,
idle timeout 30 menit, absolute lifetime 12 jam, branding, design token,
favicon, logo placeholder, typography, light/dark preference, dan app name.

**Acceptance:** Runtime settings dapat dibaca consumer module dan perubahan terkontrol.  
**Verify:** Integration, API, UI, dan security tests.

## Phase 5 — End-to-End Hardening

### T-018 Complete API and Frontend Flows

**Depends on:** T-011, T-012, T-013, T-014, T-015, T-016

Lengkapi endpoint internal /api/v1, Inertia pages, forms, loading/error/empty
states, permission visibility, dan responsive critical flows. Route memakai Ziggy
dan component tetap module-local.

**Acceptance:** Critical journey berjalan dari browser sampai persistence.  
**Verify:** Playwright, axe-core, API contract, dan keyboard review.

### T-019 Performance and Resilience Verification

**Depends on:** T-017

Benchmark 100 concurrent users dan 100.000 records. Uji P95 regular endpoint
<= 500 ms, queue retry, failed job, Redis failure, invalid module isolation,
idempotent retry, dan duplicate event handling.

**Acceptance:** Performance dan failure behavior memenuhi NFR.  
**Verify:** Load/performance report dan resilience test evidence.

### T-020 Security and Dependency Hardening

**Depends on:** T-017

Jalankan CodeQL, OWASP Dependency-Check, authorization matrix, injection tests,
session timeout, CSRF, XSS, rate-limit bypass, dan secret redaction.

**Acceptance:** Tidak ada critical/high finding terbuka dan security gate lulus.  
**Verify:** CI security reports dan security test evidence.

## Phase 6 — Release and Reuse

### T-021 Fresh Install, Upgrade, Backup, Restore

**Depends on:** T-018, T-019

Verifikasi quickstart pada instalasi Laragon bersih, migration fresh dan upgrade,
backup/restore database, Redis dependency, rollback, dan health command.

**Acceptance:** Project turunan mengikuti dokumentasi tanpa instruksi lisan.  
**Verify:** Clean-machine runbook evidence.

### T-022 Baseline Release

**Depends on:** T-020

Update documentation, changelog, known issues, verification matrix, release
note, dan evidence acceptance seluruh baseline specification.

**Acceptance:** Baseline reusable siap dipakai project turunan dan AI assistant.  
**Verify:** Release checklist dan final CI run.

## Definition of Done

Task hanya selesai jika implementasi mengikuti specification, test positif,
negatif, authorization, dan failure path tersedia, quality gate lulus,
migration/permission/audit/ULID diverifikasi, documentation diperbarui, serta
tidak ada secret, Wayfinder, Laravel Boost, atau asumsi tersembunyi.

## Risks and Mitigations

| Risk | Impact | Mitigation |
|---|---|---|
| Generator terlalu generik | High | Batasi profile pada vertical slice teruji. |
| Struktur module berubah | High | Kunci manifest, stub, dan ADR sebelum generator. |
| Starter kit berubah | Medium | Simpan verification matrix dan version policy. |
| Audit membocorkan data | High | Redaction allowlist dan security test. |
| Audit membocorkan data | High | Redaction allowlist dan security test. |
| Contract lintas module dilanggar | High | Contract test dan dependency review. |
| Runtime setting invalid | High | Schema validation, safe default, cache failure test. |
