# 03.12 Pola Komunikasi dan Eksekusi Module

## Tujuan

Dokumen ini menjelaskan cara module berkomunikasi dan menjalankan use case.
Dokumen ini menjadi acuan untuk contract/interface, event, action/command,
query/read contract, module API, shared value object, queue/job, dan batas
CQRS-lite.

Tujuannya adalah mencegah setiap module membuat pola komunikasinya sendiri.
Dokumen ini juga membedakan aturan target dari implementasi yang sudah tersedia
saat ini.

## Status baseline saat ini

Project menggunakan DDD-lite Modular Monolith. Pola default yang sudah aktif:

```text
Presentation Controller
    -> FormRequest
    -> Application Action atau Query
    -> Application Contract
    -> Infrastructure Adapter
    -> Domain/Data boundary
```

Event domain synchronous sudah digunakan pada flow impersonation. Command Bus,
integration event, queued job, dan Shared Kernel domain belum menjadi capability
aktif pada module `AccessControl` dan `UserManagement`.

## Aturan Fondasi Enterprise untuk Setiap Module

Setiap module wajib menyiapkan dan mendokumentasikan sembilan fondasi berikut:

1. `Contract/Interface` untuk boundary dan consumer nyata.
2. `Domain Event` untuk fakta internal module.
3. `Application Event` untuk koordinasi handler pada application layer.
4. `Integration Event` untuk consumer lintas module atau external system.
5. `Command` untuk mutation penting, bersama Handler dan authorization.
6. `Query/Read Contract` untuk read typed tanpa side effect.
7. `Shared Kernel` hanya bila ada value object stabil yang dimiliki dan dipakai
   minimal dua module.
8. `Facade/Module API` melalui contract publik; Facade bukan default.
9. `Queue/Job` hanya untuk pekerjaan asynchronous yang memiliki retry,
   idempotency, actor/correlation ID, dan failure contract.

Dokumen module harus menulis status, owner, dependency, acceptance criteria,
verification, dan alasan untuk setiap fondasi. Status `not applicable` tetap
harus memiliki alasan. Dengan aturan ini, baseline runtime boleh menggunakan
CQRS-lite, tetapi setiap module sudah memiliki peta evolusi enterprise yang
jelas dan tidak membuat pola baru secara sembarangan.

## Aturan contract dan module API

- Contract/interface berada pada boundary yang memiliki kebutuhan consumer.
- Contract tidak boleh mengembalikan model private adapter atau object Spatie
  secara langsung.
- DTO publik harus typed, deterministik, dan tidak membawa password, token,
  credential, atau sensitive payload.
- Public module API menggunakan contract, DTO, capability, atau public event.
- Facade tidak dibuat hanya untuk mempersingkat pemanggilan. Facade baru boleh
  dibuat jika ada API module yang stabil, consumer nyata, dan keputusan ADR.
- Dependensi lintas module wajib tercatat pada `module.json` dan diuji dengan
  contract/dependency test.

## Aturan event

### Domain Event

Domain Event dipakai untuk fakta yang sudah terjadi di dalam module. Nama event
menggunakan past tense, payload typed, dan tidak mengandung secret. Contoh yang
sudah ada adalah event impersonation.

Domain Event tidak boleh menjadi cara untuk mengakses private model module lain.
Event boleh didispatch synchronous selama side effect kecil dan langsung.

### Application Event

Application Event dipakai jika application layer perlu memberi sinyal kepada
beberapa handler dalam module yang sama. Event ini tidak menggantikan return
value use case dan tidak boleh menyembunyikan error penting.

### Integration Event

Integration Event dipakai untuk consumer lintas module atau external system.
Integration Event wajib memiliki contract yang stabil, `event_name`, version,
`event_id` ULID, `occurred_at`, `correlation_id` ULID, actor context yang aman,
dan payload yang sudah disanitasi.

Domain Event tidak otomatis menjadi Integration Event. Promosi dari domain event
ke integration event memerlukan consumer nyata dan keputusan dokumentasi.

## Aturan Action, Command, dan Query

- Application Action adalah default untuk mutation pada module saat ini.
- Action bertanggung jawab mengorkestrasi authorization, contract, transaction
  boundary, dan persistence adapter; business rule tetap pada boundary pemilik.
- Command Bus belum wajib. Command Bus baru dipakai jika jumlah handler,
  middleware, retry, audit, atau dispatch lintas entry point sudah membuat
  pemanggilan langsung sulit dikelola.
- Query digunakan untuk membaca data dan mengembalikan DTO/read contract.
- Query tidak boleh mengubah state atau melakukan side effect tersembunyi.
- `ListUsers` dan `GetUser` adalah Query internal UserManagement, bukan public
  API lintas module sampai contract read-nya disetujui.

## Aturan Shared Kernel

- Shared Kernel domain tidak aktif sebagai default project.
- `packages/StarterKit` adalah package framework reusable, bukan tempat model
  atau aturan bisnis bersama.
- Shared value object hanya boleh dibuat jika immutable, stabil, dipakai oleh
  minimal dua module, dan memiliki owner/versi yang jelas.
- Jangan memindahkan model, repository, policy, atau business service ke shared
  folder hanya untuk menghindari contract.

## Aturan Queue dan Job

- Queue/Job hanya dipakai untuk pekerjaan yang dapat berjalan asynchronous,
  lama, retryable, atau tidak boleh menahan request.
- Job wajib memiliki input typed, actor/correlation ID bila relevan, retry
  policy, failure behavior, dan idempotency strategy.
- Sensitive mutation tidak boleh dipindahkan ke queue tanpa authorization dan
  audit boundary yang tetap jelas.
- Saat ini `AccessControl` dan `UserManagement` belum memiliki Job atau queued
  listener. Jangan menambahkan queue hanya karena pola tersebut tersedia di
  baseline.

## Aturan CQRS-lite

Baseline memakai CQRS-lite, bukan CQRS penuh:

- write: Application Action + repository/domain boundary;
- read: Application Query + typed DTO/read contract;
- database dan model boleh tetap shared selama ownership module jelas;
- tidak ada read database terpisah atau event sourcing pada baseline;
- Command Bus, projection, dan asynchronous integration event hanya ditambahkan
  melalui increment dan keputusan terpisah.

## Verifikasi wajib

Setiap capability baru wajib diperiksa dengan:

- contract test untuk public interface;
- positive dan negative test untuk authorization/failure;
- architecture test untuk forbidden concrete dependency;
- event redaction test untuk payload sensitif;
- idempotency/retry test jika memakai queue atau handler retryable;
- integration test jika consumer lintas module sudah tersedia.
