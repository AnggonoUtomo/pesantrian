## Environment Matrix

| Environment | Primary Use | Target | Data | Deploy Authority |
|---|---|---|---|---|
| Local | Development | Laragon on Windows | Synthetic/local | Developer |
| CI | Automated verification | GitHub Actions runner | Ephemeral | Workflow |
| Development | Optional shared integration | Project-selected | Non-production | Developer/Tech Lead |
| Staging | QA and release rehearsal | Optional DigitalOcean Ubuntu or cPanel | Sanitized | Protected CI environment |
| Production | Real users | Optional DigitalOcean Ubuntu or cPanel | Production | Approved release workflow |

Local Laragon adalah baseline pertama. Development environment bersifat optional
dan tidak boleh menjadi alasan untuk melewati CI. Staging harus semirip mungkin
dengan production, tetapi tidak boleh memakai credential atau data production.

## Technical Baseline

- PHP 8.4+ dan Laravel 13.
- React, TypeScript strict, Inertia.js, Vite, Tailwind, dan shadcn/ui.
- PostgreSQL sebagai database utama.
- Redis untuk cache, queue, rate limit, dan idempotency bila capability tersedia.
- Ziggy untuk route frontend.
- Local filesystem untuk development; S3-compatible atau provider storage untuk
  environment shared sesuai kebutuhan module.
- Queue worker dan scheduler wajib tersedia pada staging/production. Pada cPanel,
  gunakan capability cron/queue provider yang tersedia atau tandai limitation
  sebelum release.

## Local Laragon Contract

Developer menyiapkan:

- PHP 8.4+ melalui Laragon;
- Node.js dan npm;
- PostgreSQL dan Redis local/service;
- Composer;
- project .env dari .env.example;
- storage link dan writable storage;
- queue worker serta scheduler untuk flow yang membutuhkannya.

Local setup tidak boleh memasukkan secret production. Database dapat memakai
database local dengan nama project dan user non-privileged.

Minimum verification:

- application boot;
- migration fresh;
- starter kit login/profile smoke test;
- module discovery/validation;
- frontend build;
- queue/cache/Redis connectivity;
- generator dry-run dan module test.

## Configuration Variables

Semua variable runtime berasal dari environment atau SystemSetting sesuai
ownership. Tidak ada credential yang di-hardcode.

| Group | Variables/Requirement |
|---|---|
| Application | APP_NAME, APP_ENV, APP_KEY, APP_DEBUG, APP_URL, LOG_CHANNEL, LOG_LEVEL |
| Database | DB_CONNECTION, DB_HOST, DB_PORT, DB_DATABASE, DB_USERNAME, DB_PASSWORD |
| Cache/Queue | CACHE_STORE, QUEUE_CONNECTION, REDIS_HOST, REDIS_PORT, REDIS_PASSWORD |
| Session | SESSION_DRIVER, SESSION_DOMAIN, SESSION_SECURE_COOKIE |
| Mail | MAIL_MAILER, MAIL_HOST, MAIL_PORT, MAIL_USERNAME, MAIL_PASSWORD, MAIL_FROM_ADDRESS |
| Storage | FILESYSTEM_DISK and provider-specific credentials |
| Frontend | VITE_APP_NAME and only non-secret public variables |
| Deployment | environment-specific deploy credential outside repository |

APP_KEY, database password, Redis password, mail credential, storage key, API
token, and deployment credential are secrets. VITE variables are public by
default and must never contain secret.

## Configuration Ownership

- Environment variable: infrastructure, secret, immutable deployment setting.
- SystemSetting: validated runtime setting such as rate limit, idempotency,
  session timeout, branding, and design token.
- Config file: non-secret application defaults and framework wiring.
- Database: application data and global settings storage.
- Module: schema, key, default, and behavior of settings it owns.

Only SuperSystem can mutate SystemSetting. Every mutation is validated, directly
active after validation, and audited with actor, reason, before/after, and
correlation ID.

## Secret Management

- Local secrets remain in ignored .env.
- CI secrets use GitHub Actions Environment Secrets.
- DigitalOcean secrets use protected server environment/secret mechanism and
  deployment account scope minimum.
- cPanel secrets use account-scoped environment configuration, protected file,
  or hosting secret facility supported by the provider.
- Secrets never appear in repository, generated code, logs, screenshots, test
  fixtures, browser artifacts, or error responses.
- Rotate credentials after suspected exposure and invalidate old credentials.
- Separate credentials and database users per environment.

## Deployment Target Profiles

### DigitalOcean Ubuntu

- Dedicated non-root deploy user.
- SSH key and known_hosts verification.
- Firewall, TLS, process supervisor, queue worker, scheduler, database/Redis
  connectivity, backup, and monitoring configured before production.
- Release directory or equivalent atomic deployment is recommended.
- Web server, PHP runtime, and process supervisor versions are recorded.

### cPanel

- PHP version and required extensions verified before deployment.
- Document root points only to public directory.
- Application files, storage permissions, cron, queue capability, database,
  Redis/external cache, TLS, and environment secret mechanism verified.
- SSH/API deployment credential is scoped to the account.
- If long-running queue workers or Redis are unavailable, affected features are
  blocked or an approved alternative is documented before release.

Both profiles must consume the same built artifact and pass the same application,
migration, smoke, and health checks. Provider-specific steps belong in the
deployment runbook, not in application code.

## Environment Promotion Rules

- Local changes are verified on Laragon before pull request.
- CI builds and tests from lock files.
- Staging uses sanitized data and protected credentials.
- Production requires approved release, backup evidence, migration plan, and
  rollback/forward-fix plan.
- No manual production code edit.
- Environment drift is recorded and corrected through infrastructure/configuration
  change.

## Open Decisions

- Exact PHP, Node.js, PostgreSQL, and Redis patch versions per target.
- DigitalOcean topology versus cPanel capability per project.
- Backup destination, retention, monitoring, and alerting provider.
- Domain, TLS certificate, mail provider, and storage provider per project.
- Queue strategy when cPanel cannot run persistent workers.

## Acceptance Criteria

- Laragon developer can bootstrap from .env.example without production secrets.
- CI, staging, and production variables are separated and documented.
- Secret scan finds no credential in repository or artifact.
- DigitalOcean and cPanel compatibility checks are explicit before deployment.
- Runtime settings are owned by modules and persisted through SystemSetting.
- Environment promotion uses the same tested artifact.
- Missing infrastructure capability blocks release with actionable diagnostic.
