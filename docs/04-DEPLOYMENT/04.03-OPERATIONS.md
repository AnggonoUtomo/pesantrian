## Operational Objectives

- Menyediakan evidence bahwa aplikasi dan dependency utama sehat.
- Menghubungkan log, queue, audit, dan incident melalui correlation ID.
- Memulihkan layanan tanpa mengubah data secara manual.
- Memastikan backup benar-benar dapat direstore.
- Menjaga secret dan sensitive payload tidak muncul pada observability output.
- Menjalankan prosedur yang kompatibel dengan DigitalOcean Ubuntu maupun cPanel
  bila capability target tersedia.
- Monitoring eksternal adalah capability optional yang dapat diaktifkan dan
  dikonfigurasi melalui SystemSetting sesuai project turunan.

## Monitoring Baseline

Monitor dan alert berikut bila capability monitoring tersedia:

- HTTP availability, error rate, latency, dan P95 endpoint regular.
- PHP/Laravel exception rate berdasarkan environment dan release identifier.
- Database connection, slow query, lock, storage, migration status, dan backup age.
- Redis connectivity, memory, eviction, latency, dan queue backend availability.
- Queue depth, failed jobs, retry rate, oldest pending job, dan worker status.
- Scheduler heartbeat dan missed task.
- Filesystem/storage capacity, write failure, media processing failure, dan TLS
  certificate expiry.
- Module registry status, invalid/disabled module, and diagnostic count.
- Security events: authorization failure spike, impersonation, setting change,
  rate-limit violation, dan login anomaly.

Baseline wajib tetap menghasilkan structured log dan diagnostic internal tanpa
bergantung pada provider monitoring eksternal. Integrasi monitoring, threshold,
dan notification channel dapat diaktifkan melalui SystemSetting; perubahan
konfigurasi wajib diaudit.

Log wajib structured, memiliki timestamp, level, environment, release identifier,
module, correlation ID, actor ID bila aman, dan sanitized context. Jangan log
password, token, credential, secret, raw sensitive payload, atau full request
body tanpa allowlist.

## Health Checks

Application menyediakan health/diagnostic command dan endpoint sesuai deployment
profile. Minimum check:

1. Application boot dan configuration load.
2. Database connection dan schema/migration compatibility.
3. Redis connection.
4. Queue backend dan worker heartbeat.
5. Scheduler heartbeat.
6. Storage writable dan media disk availability.
7. Module discovery/registry, enabled module, dan invalid module diagnostic.
8. Cache read/write.
9. External mail/storage dependency bila required oleh release.

Health check membedakan liveness dan readiness. Liveness hanya memastikan process
hidup. Readiness memastikan dependency wajib siap menerima traffic. Response tidak
boleh membocorkan credential, connection string, atau internal stack trace.

Post-deployment smoke test minimal menjalankan starter kit login reuse, module
discovery, AccessControl authorization, UserManagement access, AuditLog write,
dan SystemSetting read/guard.

## Queue and Scheduler Operations

- Queue worker menjalankan retry policy yang ditentukan module.
- Failed job tidak dihapus sebelum diagnosis dan evidence tersimpan.
- Retry/replay hanya dilakukan setelah idempotency dan side effect diverifikasi.
- Job memiliki correlation ID, actor context yang aman, dan release identifier.
- Scheduler memiliki single-run protection dan heartbeat.
- Worker restart dilakukan melalui process supervisor pada VPS atau capability
  process/cron cPanel yang disediakan hosting.
- Redis outage harus menghasilkan diagnostic dan safe failure; jangan silently
  process mutation yang membutuhkan idempotency.

## Backup and Restore

Backup mencakup:

- MySQL database dan migration metadata.
- User-uploaded/media storage.
- Environment/configuration reference tanpa secret plaintext.
- Release manifest dan deployment metadata.

Rules:

- Backup terenkripsi saat transit dan saat tersimpan.
- Backup tidak disimpan hanya pada host production yang sama.
- Retention mengikuti kebijakan environment/project.
- Backup diberi timestamp, release identifier, checksum, dan owner.
- Restore test dilakukan berkala pada environment terisolasi.
- Setelah restore, jalankan migration/schema check, health check, module registry,
  audit integrity, dan smoke test.
- Backup failure menjadi alert dan release blocker bila backup required.

Target pemulihan baseline disimpan sebagai runtime setting pada SystemSetting:

- `operations.rto_hours`: default maksimum 4 jam.
- `operations.rpo_hours`: default maksimum 24 jam.

Hanya `SuperSystem` yang dapat mengubah kedua setting, perubahan langsung aktif
setelah validation, dan perubahan wajib diaudit. Project turunan dapat memilih
target lebih ketat, tetapi tidak boleh lebih longgar tanpa risk acceptance.

Project turunan dapat menetapkan target lebih ketat, tetapi tidak boleh lebih
longgar tanpa risk acceptance yang terdokumentasi.

SystemSetting dan AuditLog termasuk data penting. AuditLog retention minimum satu
tahun sesuai baseline. Restore tidak boleh menghasilkan duplicate side effect
pada queue atau idempotency record tanpa review.

## Maintenance

Gunakan Laravel maintenance mode untuk perubahan yang memerlukan downtime atau
migrasi non-compatible. Sebelum maintenance:

- announce impact dan window;
- backup dan migration plan tersedia;
- queue drain/pause strategy ditentukan;
- health check dan rollback path siap;
- operator tercatat.

Setelah maintenance:

- migration status diverifikasi;
- cache/config dibersihkan sesuai release plan;
- queue dan scheduler diaktifkan;
- smoke test dan monitoring diperiksa;
- maintenance mode dimatikan hanya setelah readiness lulus.

## Incident Severity

| Severity | Definition | Response |
|---|---|---|
| SEV-1 | Layanan utama unavailable, data loss risk, atau security compromise | Immediate owner, containment, stakeholder escalation, recovery |
| SEV-2 | Fitur penting terganggu tanpa workaround memadai | Assigned response, mitigation, regular update |
| SEV-3 | Dampak terbatas dengan workaround tersedia | Normal priority, root-cause follow-up |

Incident record wajib memiliki incident ID, start/end time, reporter, impact,
affected environment/release/module, timeline, evidence, mitigation, decision,
communication, recovery verification, root cause, dan corrective action.

Security incident tidak boleh diekspos melalui public error response. Preserve
relevant log/audit evidence dan batasi akses incident record.

## Incident Response

1. Detect dan buat incident record.
2. Triage severity, scope, environment, release, dan affected module.
3. Contain: pause deployment, isolate invalid module, disable unsafe job, atau
   aktifkan maintenance mode bila diperlukan.
4. Mitigate dengan rollback atau forward-fix yang disetujui.
5. Verify health, readiness, queue, database, audit, dan critical user flow.
6. Communicate status dan residual risk.
7. Close dengan root-cause analysis, action owner, dan due date.

Tidak boleh memperbaiki production dengan edit source manual tanpa perubahan
tercatat. Rollback aplikasi tidak otomatis membatalkan migration; gunakan
backward-compatible migration atau forward-fix.

## Routine Maintenance

| Frequency | Activity |
|---|---|
| Every deploy | Health, readiness, smoke, queue, registry, error rate |
| Daily or project-defined | Backup status, failed jobs, scheduler, storage, TLS |
| Weekly | Dependency/security report, log review, queue and database review |
| Monthly or project-defined | Restore test, access review, secret rotation review |
| Before release | Migration rehearsal, rollback rehearsal, capacity and backup check |

Frekuensi yang bergantung pada project wajib ditetapkan pada deployment runbook
project turunan tanpa mengubah baseline safety requirement.

## Platform Notes

### DigitalOcean Ubuntu

Gunakan non-root deploy user, firewall, TLS, process supervisor, queue worker,
scheduler, database/Redis access control, external backup, dan monitoring.
Dokumentasikan service status dan log location.

### cPanel

Verifikasi PHP extension, document root ke public, storage permission, cron,
queue/Redis capability, database backup, TLS, environment secret facility, dan
provider health/monitoring. Bila queue worker atau Redis tidak tersedia, fitur
yang bergantung padanya harus diblokir atau memakai alternative yang disetujui.

## Open Decisions

- Tool monitoring dan alerting provider bersifat optional per project.
- Backup retention serta restore test frequency final.
- Topology Redis/queue dan process supervisor pada target cPanel.
- Incident contact/escalation roster.

## Acceptance Criteria

- Health/readiness check mencakup application, database, Redis, queue, scheduler,
  storage, cache, dan module registry.
- Structured log dapat dicari melalui correlation ID tanpa sensitive payload.
- Backup dan restore test memiliki evidence.
- Failed job, invalid module, dan cache/Redis failure memiliki prosedur aman.
- Incident record dan severity process dapat digunakan oleh operator baru.
- DigitalOcean dan cPanel capability checks tersedia sebelum release.
- AuditLog dan SystemSetting perubahan tercakup dalam monitoring/audit review.
