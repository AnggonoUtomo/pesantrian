## Purpose

Dokumen ini mencegah konflik antara SAKAAI dan Laravel Engineering Documentation.
SAKAAI mengatur bagaimana AI memilih context, merencanakan, menjalankan tool,
memvalidasi, dan mencatat evidence. Folder docs mengatur apa yang harus dibangun
pada Laravel project, termasuk requirement, architecture, module, test, dan
deployment contract.

SAKAAI bukan pengganti requirement Laravel. Baseline Laravel bukan pengganti
governance SAKAAI.

## Conflict Precedence

When documents conflict, apply this order:

1. Direct user decision in the current project context.
2. Accepted project ADR or explicit project decision.
3. Laravel baseline requirement/design contract in docs/00–05.
4. Laravel framework/kernel contract in docs/06–07.
5. SAKAAI Laravel template and engineering specification.
6. Generic SAKAAI guidance, skills, and examples.
7. Historical, deprecated, or generated documentation.

SAKAAI governance rules remain mandatory at every level unless a higher-priority
system or user instruction says otherwise. A conflict must not be silently
resolved. Record the conflict, impact, owner, and resolution in an ADR or
project decision record.

### Transactions to Application Actions

SAKAAI Transactions and Laravel Application Actions are compatible concepts:

- Transaction class is used when the main responsibility is an atomic persistence
  boundary across one or more tables.
- Application Action is the public application use case and orchestration entry
  point.
- An Action may call one Transaction, repository contract, domain service, or
  event publisher.
- A Transaction must not become a controller, request validator, policy, or
  cross-module concrete caller.
- If an Action only coordinates a single atomic write, the transaction boundary
  may be implemented inside the Action.
- Name the class by use case, keep one responsibility, and test both outcome and
  rollback behavior.

Example mapping:

| SAKAAI | Baseline |
|---|---|
| CreateUserTransaction | CreateUserAction plus UserPersistenceTransaction when needed |
| CreateUserDTO | Application/DTO/CreateUserData |
| UserModuleContract | UserManagement public contract |
| UserPolicy | Presentation/Policies/UserPolicy |
| UserCreatedEvent | Domain/Events/UserCreated with ULID |

## ULID Project Rule

ULID is the authoritative identifier standard for this Laravel baseline.

- Every table primary key and foreign key uses ULID.
- Route binding, DTO, API resource, event, job, audit actor, subject, fixture,
  and correlation identifiers use ULID.
- Integer auto-increment and UUID are not allowed for entity identity.
- SAKAAI examples using int are illustrative and must be adapted to ULID.
- New project documentation must record identifier choice in specification and
  database design before implementation.
- Generator, migration, model, factory, seeder, API, and test output must be
  checked for ULID consistency.

## SAKAAI CLI and docs Integration

SAKAAI CLI remains the governance/tooling runner. The Laravel documentation root
is docs/, not a hardcoded local workspace name.

Required CLI integration contract:

- Detect docs/ as the documentation root when running from a Laravel project.
- Support an explicit docs root argument for project layouts that differ.
- status scans docs, docs/Projects, and SAKAAI separately.
- validate checks metadata, relative links, numbering, project template shape,
  and forbidden local workspace paths.
- audit hashes authoritative documentation and records the selected root.
- health checks the SAKAAI directory, docs baseline, project intake template,
  and Laravel preset.
- install copies SAKAAI governance and selected architecture template only.
- docs/ is initialized or copied manually by the project owner; SAKAAI installer
  must not create, overwrite, merge, or delete project documentation.
- CLI output identifies source root, docs root, project slug, and validation scope.

Target command contract:

- node cli/sakaai.js status --docs docs
- node cli/sakaai.js validate --docs docs
- node cli/sakaai.js audit --docs docs
- node cli/sakaai.js health --docs docs

Until the CLI accepts --docs, callers must pass the repository/project root
according to the installed CLI version and treat docs integration as a planned
implementation task. CLI must never silently scan a different docs directory.

## SAKAAI-Recognized Project Intake

A project documentation folder is recognized when it contains:

- Projects/{project-slug}/README.md;
- specification.md;
- implementation-plan.md;
- roadmap.md;
- task.md;
- decisions/;
- planning/;
- project mode, starter kit status, module inventory, owner, and status;
- at least one task with acceptance and verification fields.

Supported modes:

- Greenfield: no Laravel starter kit detected.
- Existing Starter Kit: starter kit detected; reuse existing capabilities.
- Module Extension: only a new module or bounded capability is added.

The intake procedure is:

1. Detect project source and documentation root.
2. Read AGENTS, SAKAAI gate, and relevant baseline context.
3. Inventory existing framework, packages, modules, routes, migrations, permission,
   events, settings, and tests.
4. Select project mode.
5. Copy Projects/_TEMPLATE to the project slug.
6. Record decisions and Open Decisions.
7. Create specification before implementation.
8. Break work into incremental tasks.
9. Execute and verify one increment at a time.
10. Update execution log, known issues, and release evidence.

## Incremental Implementation Rule

Every new module or project change uses incremental-implementation:

- One increment has one narrow outcome.
- Every increment has task ID, dependency, acceptance criteria, focused tests,
  verification command/evidence, and documentation update.
- Do not mix discovery, architecture, migration, UI, and deployment into one
  unbounded task unless the plan explicitly makes them one vertical slice.
- Stop after a failed verification and fix the increment before proceeding.
- Record changed files, test result, decision, risk, and next step in planning/
  execution-log.md.
- A module is ready only after contract, authorization, audit, migration, test,
  and relevant browser/CI verification pass.

## Validation Contract

Validation runs at four levels:

1. Documentation: metadata, relative links, numbering, authority, Open Decision,
   and template shape.
2. Architecture: module boundary, contract dependency, ULID, forbidden package,
   and generated structure.
3. Code: formatting, static analysis, tests, build, security, and dependency scan.
4. Operations: migration, health, queue, cache, backup/restore, smoke, RTO, RPO,
   and rollback evidence.

A failed lower-level check cannot be hidden by a successful higher-level check.
Validation output must include scope, files, rule, result, diagnostic, and
remediation. No tool may report success when files were skipped silently.

## Acceptance Criteria

- SAKAAI governance and Laravel docs have explicit authority boundaries.
- Transaction and Action mapping is documented and testable.
- ULID rule overrides incompatible illustrative examples.
- Project Intake template is discoverable and machine-recognizable.
- Incremental implementation has task/evidence requirements.
- CLI docs integration has explicit root and command contract.
- Relative links work when documentation is mounted as docs/.
- Conflict resolution always produces a recorded decision.
