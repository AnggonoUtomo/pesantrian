# 05.04 ADR-0002: Documentation Standard

## Decision Scope

Keputusan ini berlaku untuk seluruh dokumentasi starter kit, termasuk specification
00 sampai 05, implementation 03, deployment 04, decision/ADR 05, framework 06,
dan kernel 07. Project turunan boleh menambah dokumen melalui aturan yang sama.

## Context

Dokumentasi project harus dapat digunakan lintas peran dan tidak bergantung pada
pengetahuan yang hanya ada di percakapan. AI assistant harus dapat memuat
context secara bertahap, menemukan keputusan yang berlaku, membedakan fakta
dari Open Decision, dan menelusuri requirement sampai verification evidence.

Dokumentasi juga menjadi baseline reusable untuk project turunan, sehingga
struktur, numbering, ownership, dan status tidak boleh berubah secara informal.

## Decision

### Numbering and File Naming

- Dokumen lifecycle utama memakai format NN.MM pada filename dan heading.
- NN adalah kelompok lifecycle: 00 context, 01 requirements, 02 design,
  03 implementation, 04 deployment, 05 decisions, 06 framework, 07 kernel.
- MM adalah urutan prioritas baca dalam kelompok tersebut.
- Filename harus diawali nomor urut agar file explorer mengurutkan prioritas.
- Judul heading utama harus sama dengan identifier filename.
- ADR memakai format 05.MM-ADR-NNNN-SLUG.md dan berada di 05-DECISIONS/ADR.
- Perubahan nomor atau pemindahan dokumen wajib dicatat pada ADR/changelog dan
  memperbarui seluruh cross-reference.
- Nama file memakai kebab-case uppercase sesuai convention repository; jangan
  membuat alias filename yang membingungkan.

### Required Document Metadata

Specification, design, implementation, deployment, dan ADR wajib memiliki:

- title dan document identifier;
- version, status, date, owner, audience;
- depends on dan related references;
- purpose/scope;
- acceptance criteria;
- verification method atau evidence expectation;
- Open Decisions bila ada;
- revision history.

Dokumen sederhana seperti glossary atau changelog dapat memakai subset metadata,
tetapi tetap harus memiliki owner, status, dan revision history.

### Status Vocabulary

- Draft: sedang disusun dan belum menjadi contract final.
- Accepted: keputusan atau dokumen disetujui sebagai baseline.
- In Progress: implementasi atau review sedang berjalan.
- Deprecated: masih berlaku untuk legacy tetapi tidak dipakai untuk perubahan baru.
- Superseded: digantikan dokumen/ADR lain dengan reference jelas.
- Archived: tidak berlaku untuk implementasi aktif dan dipertahankan sebagai sejarah.

Status Accepted tidak berarti feature sudah diimplementasikan; implementation
status dan evidence harus ditulis terpisah.

### Open Decision Rules

- Hal yang belum diputuskan ditulis sebagai Open Decision, bukan fakta.
- Setiap Open Decision memiliki ID, pertanyaan, impact, owner, dan resolution
  criteria bila keputusan tersebut memblokir implementasi.
- Jawaban user atau keputusan architecture harus dipindahkan dari percakapan ke
  dokumen terkait.
- Setelah resolved, hapus ambiguity, catat keputusan, update references, dan
  tambahkan revision history.
- AI assistant dilarang mengisi Open Decision dengan tebakan.

### Context Loading and AI Usage

Context loading order:

1. README.md dan AGENTS.md.
2. 00 context dan baseline direction.
3. Relevant requirements 01.
4. Related design/contracts 02.
5. Implementation pattern, tests, and task plan 03.
6. Deployment/operations/release 04.
7. ADR, known issues, and changelog 05.
8. Framework 06 dan kernel 07 hanya setelah prerequisite tersedia.

AI assistant wajib:

- membaca dokumen prerequisite sebelum mengubah dokumen downstream;
- mengikuti keputusan Accepted dan menandai contradiction;
- tidak mengarang dependency, API, permission, environment, atau security rule;
- menggunakan interview-me saat intent/requirement belum jelas;
- menggunakan idea-refine untuk mengevaluasi alternatif sebelum keputusan;
- menggunakan spec-driven-development sebelum implementasi;
- menggunakan planning-and-task-breakdown untuk task executable;
- menggunakan context-engineering untuk menjaga context pack dan aturan agent;
- menambahkan acceptance criteria dan verification untuk setiap perubahan.

### Traceability

Requirement diberi ID stabil dan ditelusurkan ke:

Requirement → Design/Contract → Implementation Task → Test → Release Evidence.

Perubahan terhadap API, database, module boundary, permission/security model,
deployment, atau operational target wajib memperbarui semua node traceability
yang terdampak.

### Documentation Change Workflow

1. Identifikasi scope dan audience.
2. Baca prerequisite sesuai context loading order.
3. Interview bila intent atau decision belum jelas.
4. Refine alternatif dan trade-off bila dibutuhkan.
5. Update specification/design sebelum implementation document.
6. Pecah implementation menjadi task dan verification.
7. Perbarui cross-reference, changelog, known issue, atau ADR.
8. Jalankan link/filename/numbering consistency check.
9. Review owner dan tandai status yang benar.

Perubahan dokumentasi tidak boleh menyalin keputusan yang bertentangan dari
dokumen authoritative. Jika terjadi konflik, buat ADR atau update authority map.

### Acceptance and Verification

Dokumen dianggap ready bila:

- numbering dan filename benar;
- status, owner, dependency, scope, acceptance, dan verification tersedia;
- Open Decision tidak disamarkan sebagai fakta;
- cross-reference target tersedia dan tidak stale;
- terminology konsisten dengan glossary;
- implementation claim memiliki test/evidence expectation;
- tidak mengandung Wayfinder atau Laravel Boost;
- instruksi dapat dipahami developer, QA, DevOps, dan AI assistant tanpa oral
  instruction tambahan.

## Consequences

### Positive

- Navigasi dan urutan membaca konsisten.
- Onboarding dan AI context loading lebih dapat diprediksi.
- Keputusan dapat ditelusuri dari intent sampai evidence.
- Perubahan kontrak lebih aman dan mudah direview.
- Dokumentasi reusable untuk project turunan.

### Negative

- Perubahan kecil dapat membutuhkan update metadata dan cross-reference.
- Owner harus menjaga status dan Open Decision tetap akurat.
- Traceability menambah pekerjaan awal sebelum implementasi.
- Renumbering dokumen lama memerlukan migration/reference update.

## Rejected Alternatives

| Alternative | Reason Rejected |
|---|---|
| Dokumentasi bebas tanpa numbering | Prioritas baca dan dependency menjadi ambigu |
| Keputusan hanya di chat | Tidak reusable dan tidak dapat diverifikasi |
| Satu dokumen besar untuk semua lifecycle | Context terlalu berat dan ownership tidak jelas |
| AI boleh mengisi ambiguity | Menghasilkan asumsi tersembunyi dan risiko implementasi |
| Status hanya Draft/Final | Tidak cukup membedakan accepted, deprecated, dan superseded |

## Compliance Checklist

- [ ] Filename dan heading mengikuti NN.MM.
- [ ] Metadata wajib tersedia.
- [ ] Dependency dan cross-reference valid.
- [ ] Requirement/design/task/test traceable.
- [ ] Open Decision memiliki owner/impact.
- [ ] Acceptance criteria dan verification tersedia.
- [ ] Changelog/revision history diperbarui.
- [ ] No forbidden dependency reference.
- [ ] Owner review selesai.
