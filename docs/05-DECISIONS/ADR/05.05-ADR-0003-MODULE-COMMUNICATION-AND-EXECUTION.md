# 05.05 ADR-0003: Pola Komunikasi dan Eksekusi Module

## Status

Accepted

## Date

2026-08-06

## Context

Project sudah memiliki `AuthorizationCapability`, beberapa Application Action,
Application Query, dan Domain Event impersonation. Namun istilah Command,
Application Event, Integration Event, Queue/Job, Shared Kernel, Facade, dan
CQRS dapat ditafsirkan berbeda oleh setiap module.

Jika tidak diberi batas, module baru dapat membuat concrete dependency lintas
module, Facade tanpa contract stabil, queue tanpa idempotency, atau mengklaim
CQRS penuh padahal hanya memisahkan Action dan Query.

## Decision

1. Public module API menggunakan contract, DTO, capability, atau public event.
   Facade bukan default.
2. Application Action menjadi pola default untuk mutation synchronous.
3. Application Query menjadi pola default untuk read dan mengembalikan typed
   DTO/read contract.
4. Domain Event dipakai untuk fakta internal module. Application Event dan
   Integration Event dibuat hanya jika consumer nyata sudah ada.
5. Integration Event wajib memiliki event identity, version, timestamp,
   correlation ID ULID, dan payload sanitized.
6. Queue/Job bukan default. Queue hanya digunakan bila ada kebutuhan
   asynchronous, retry, durasi panjang, atau pemisahan request.
7. Shared Kernel domain tidak diaktifkan. `packages/StarterKit` tetap menjadi
   reusable framework package, bukan Shared Kernel business.
8. Baseline menggunakan CQRS-lite: Action untuk write dan Query untuk read,
   tanpa Command Bus, projection, read database terpisah, atau event sourcing.

## Kondisi Implementasi Saat ADR Disetujui

- Contract/interface: sudah digunakan pada AccessControl dan UserManagement.
- Domain Event: sudah digunakan untuk start/stop impersonation.
- Application Event: belum tersedia.
- Integration Event dan consumer AuditLog: sudah tersedia secara synchronous
  melalui event activity version 1 dari AccessControl dan UserManagement.
- Command Bus dan queued Job: belum digunakan.
- Shared Kernel: belum tersedia dan memang bukan baseline.
- CQRS: baru berupa pemisahan Action/Query, yaitu CQRS-lite.

Pembaruan implementasi 6 Agustus 2026: AuditLog menjadi consumer nyata.
Consumer menolak version yang tidak didukung, memakai `event_id` unik untuk
idempotency, mempertahankan `correlation_id`, dan mempropagasikan failure agar
mutation sensitif tetap fail-closed. Queue tetap tidak digunakan sesuai
keputusan ADR ini.

## Consequences

### Positif

- Consumer lintas module memiliki boundary yang jelas.
- Module baru tidak membuat pola command/event/queue sendiri-sendiri.
- Implementasi saat ini dapat dilanjutkan tanpa menambah infrastruktur yang
  belum dibutuhkan.
- Peralihan ke Integration Event atau Queue dapat dilakukan melalui increment
  dan contract yang terdokumentasi.

### Batasan

- Belum ada asynchronous processing untuk event impersonation.
- AuditLog belum menjadi consumer event.
- Query masih internal module dan belum menjadi read API lintas module.
- `correlation_id` wajib ditambahkan saat event dipromosikan ke integration
  event atau queued workflow.

## Alternatives Considered

### CQRS penuh sejak awal

Ditolak untuk baseline karena belum ada kebutuhan projection, read database,
atau beban read/write yang membenarkan kompleksitas tambahan.

### Facade sebagai API setiap module

Ditolak karena Facade dapat menyembunyikan contract dan mendorong consumer
bergantung pada service konkret. Contract typed lebih mudah diuji dan di-version.

### Shared Kernel untuk semua DTO/value object

Ditolak karena shared kernel yang terlalu cepat membuat boundary module kembali
terikat. Shared value object harus menunggu kebutuhan lintas module yang nyata.

## Consequence untuk Module Berikutnya

Sebelum membuat module baru, dokumentasi module wajib menyatakan:

- contract publik yang dimiliki;
- query/read contract yang diekspos;
- event domain/application/integration yang dipakai;
- apakah ada queue/job dan bagaimana idempotency-nya;
- alasan jika memakai Facade atau shared value object;
- alasan jika keluar dari CQRS-lite baseline.

## Fondasi Enterprise yang Wajib Disiapkan

Keputusan ini tidak mengharuskan semua capability enterprise aktif sejak hari
pertama, tetapi setiap module wajib menyiapkan keputusan dan boundary untuk:

- Contract/Interface;
- Domain Event;
- Application Event;
- Integration Event;
- Command dan Handler;
- Query/Read Contract;
- Shared Kernel;
- Facade/Module API; dan
- Queue/Job.

Setiap item harus memiliki status, owner, dependency, acceptance criteria,
verification, serta alasan jika belum aktif. Runtime default tetap CQRS-lite.
Perubahan ke CQRS hybrid atau CQRS penuh harus dibuat sebagai increment baru
dengan ADR, bukan melalui perubahan diam-diam di dalam module.
